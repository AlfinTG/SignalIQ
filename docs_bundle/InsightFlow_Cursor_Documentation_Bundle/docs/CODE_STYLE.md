# Code Style and Engineering Standards

## 1. General

- Prefer simple, explicit code over clever abstractions.
- Use consistent naming and keep functions short enough to review.
- Avoid adding dependencies unless they clearly save time or improve reliability.
- Do not duplicate business calculations across multiple components; keep calculations in testable utility functions.
- No dead controls, placeholder click handlers, fake loading indicators, or commented-out alternative implementations left behind.

## 2. TypeScript / React

- Enable strict TypeScript checking.
- Avoid `any`; use safe `unknown` parsing and narrow types.
- Define domain types for feedback, issue status, analysis results, API responses, filters, and reports.
- Use functional components and hooks; keep components focused.
- Do not mutate arrays/objects in place when changing React state.
- Use stable keys from feedback/issue IDs.
- Separate pure calculations from UI rendering.
- Handle loading, empty, success, and error states explicitly.
- Do not expose server-only secrets through Vite `VITE_*` variables.
- Keep localStorage parsing inside a small validated persistence layer.

## 3. Python / FastAPI

- Use type annotations and Pydantic request/response schemas.
- Separate route handlers from provider-specific helpers where it improves testability.
- Use `httpx`/SDK timeouts and map provider failures to useful HTTP errors.
- Never return stack traces or secrets in client error payloads.
- Avoid blocking long-running external SDK operations on the event loop; use supported async methods or a bounded thread/background-job approach.
- Bound request sizes, row counts, text lengths, and any polling timeout.
- Keep temp-file creation/cleanup safe and ensure server paths are independent of current shell directory.
- Mock external SDKs in automated tests.

## 4. AI output handling

- Request structured output where supported.
- Validate every field against strict enums/length bounds.
- Align results to stable IDs, not array order alone.
- Ignore model-provided aggregate counts and calculate metrics in code.
- Treat comment text as untrusted content, not instructions to the model/system.
- Provide a deterministic fallback only when clearly labelled as demo/rules-based.
- Do not claim model confidence calibration unless actually established.

## 5. Error messages and logs

- User-facing errors explain what happened and the next action, without stack traces or provider internals.
- Server logs may include request/job IDs and a sanitized error summary, not API keys, raw customer text, or full provider payloads.
- Differentiate missing credentials, invalid input, provider failure, timeout, and an unavailable result.

## 6. Formatting and quality tools

- Use the chosen formatter/linter if configured (for example, Prettier/ESLint for frontend and Ruff for backend).
- Keep lockfiles committed when generated by the package manager.
- Do not invent a passing test result. Run commands and record the actual outcome.
- Keep README/setup commands aligned with the final folder structure.
